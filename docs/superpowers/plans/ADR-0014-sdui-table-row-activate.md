# ADR-0014 — Активация строки ТЧ на сервере (`table.rowActivate`) и отказ добавления по правилу

- **Статус:** Accepted (реализовано во фронте; часть следствий ждёт бэка — §7)
- **Дата:** 2026-07-30
- **Owner (предложил):** пользователь (цель, решение по UI отказа); формализация — фронт
- **Затрагивает:** frontend (`fin-web` — новый хук `lib/hooks/use-row-activate.ts`, `complex-editable-table.tsx`, `editable-table.tsx`), webbuh-api (композер `actions`, handler ИПН — см. [backend-handoff-table-row-activate.md](backend-handoff-table-row-activate.md))
- **Опирается на (НЕ переоткрывает):** [ADR-0011](ADR-0011-sdui-editable-tables.md) (модель строк `{rowId,…}`, table-level sync §3.4, canon только от сервера, server-driven дисциплина §2.5), [ADR-0013](ADR-0013-sdui-complex-tables.md) (master-detail §4.2, отложенная опция §4.4), ADR-0022 (доменные команды ТЧ, префикс `table.`)
- **Связано с:** [frontend-spec-table-row-activate.md](frontend-spec-table-row-activate.md) (входная спека бэка), [frontend-spec-complex-tables-reference-cell.md](frontend-spec-complex-tables-reference-cell.md), [2026-07-28-scrum-284-events-contract.md](2026-07-28-scrum-284-events-contract.md) (`behavior`, «команда приходит готовой»)
- **Прувпойнт:** `RegistratsiyaZayavleniyPoVychetamIPN` — master `VychetyIPN` + detail `GrafikVycheta`

---

## 1. Контекст

### 1.1 Разрыв, который закрывается

ADR-0013 §4.2 сделал master-detail-фильтр презентационным: выбор строки master живёт
только на клиенте, round-trip не требуется. Плата за это — сервер не знает, какая строка
master активна, и правило, зависящее от текущей строки, выразить нечем.

Эталон «Регистрация заявлений по вычетам ИПН» такое правило содержит: график вычета
вводится только вычету с `ВидПредоставленияВычета = По периодическим платежам`; в 1С за
это отвечает `ВычетыИПНПриАктивизацииСтроки` — кнопка «Добавить» в ТЧ «График вычета»
отражает **текущую** строку ТЧ «Вычеты ИПН». ADR-0013 §4.4 предусмотрел это как
отложенную опцию; настоящий ADR её вводит.

### 1.2 Что уже закрыто сервером без правок фронта

Доступность «Добавить» по составу «Вычетов ИПН» сервер считает сам (OPEN, изменение ТЧ,
смена физлица) и шлёт `setProp allowAdd`; ошибочно добавленную строку графика снимает с
пояснением. Не хватало ровно одного — реакции на клик по строке.

### 1.3 Что НЕ переоткрывается

Модель строк и table-level sync (ADR-0011 §3.1/§3.4), «canon — только от сервера»,
презентационный master-detail-фильтр (ADR-0013 §4.2), контракт `behavior` и правило
«команда приходит готовой строкой» (SCRUM-283/284).

---

## 2. Решение — обзор

1. TABLE, у которой в `actions` есть элемент с `trigger: "activate"`, на смену активной
   строки шлёт `COMMAND` с готовой командой бэка и `value: { rowId }`.
2. Дедуп по `rowId`: повторная активация той же строки round-trip не порождает.
3. Ответ применяется штатным путём патчей — специальной обработки нет.
4. Отказ добавления по правилу показывает **сервер**: кнопка «Добавить» у detail-ТЧ не
   гаснет и не прячется (эталон 1С), клик уходит на сервер, тот снимает строку и
   объясняет причину своим `notify`.

Правило целиком остаётся на сервере. Фронт сообщает, какая строка активна, и применяет
патчи; своей копии правила и своего текста ошибки у него нет.

---

## 3. Решение — детально

### 3.1 Точка расширения — хук, а не `table-node.tsx`

Входная спека называла `table-node.tsx`, но в `fin-web` этот файл — только маршрутизатор
(`editable → EditableTable | ComplexEditableTable`, иначе read-only). Понятие «выбранная
строка» живёт в двух компонентах, поэтому логика вынесена в
`lib/hooks/use-row-activate.ts` и подключена в обоих:

| Компонент | Момент вызова |
|---|---|
| `ComplexEditableTable` | `handleRowClick` — там же, где публикуется `<binding>.__selectedRowId` для master-detail |
| `EditableTable` | `onClick` строки, рядом с `setSelectedIndex` |

Read-only TABLE понятия активной строки не имеет — там хук не подключается.

### 3.2 Триггер — одиночный клик, не двойной

`activate` у TABLE = одиночный клик / смена активной строки (в LIST тот же `trigger`
означает двойной клик — это другой узел и другая семантика, `nav.rowOpen`). Новое
понятие «активная строка» не вводится: используется существующий момент публикации
выбора для master-detail. Клавиатурной навигации по строкам в таблицах сейчас нет —
когда появится, она обязана звать тот же хук.

### 3.3 Дедуп по `rowId` и его сброс

Клик по строке — самая частая операция в таблице, а ответ на повторную активацию той же
строки идентичен. `lastActivatedRef` хранит последний отправленный `rowId`; сбрасывается
при смене массива строк по binding таблицы (подписка `useBindingValue(node.binding)`) —
после `setValue` прежнего `rowId` может уже не быть.

### 3.4 `behavior` — как прислал бэк, без фолбэков «на всякий случай»

Команда немутирующая: `flushPendingTables: false` (клик по строке не должен стоить
flush'а незакоммиченного ввода), `resetsDirty: false`, `closeAfter: false`. Фронт
пробрасывает объект в `dispatch` как есть; асимметричные дефолты `dispatch.ts`
(`flush ?? true`) срабатывают только при отсутствии `behavior`.

### 3.5 Применение ответа

Ответ — обычные патчи, чаще всего `setProp` на **другой** узел (detail-таблицу).
Спец-обработки не потребовалось: `applyPatches` возвращает новый объект узла по пути до
корня, ноды не мемоизированы, поэтому `props.allowAdd` перечитывается на каждом рендере
и тулбар перерисовывается. Зафиксировано тестом, чтобы будущая мемоизация нод это не
сломала молча.

### 3.6 Отказ «Добавить» — кнопка остаётся активной (решение владельца)

`TableToolbar` при `allowAdd={false}` **скрывал** кнопку целиком. Для detail-ТЧ это
неверно вдвойне: пользователь не видит ни кнопки, ни причины, а эталон 1С показывает
кнопку и отвечает сообщением.

Принято: у ТЧ с `masterTable/masterKey/detailKey` `allowAdd` — это **состояние правила**
(сервер гоняет его патчами), а не структурный запрет, поэтому кнопка не прячется:

```ts
const showAdd = allowAdd || isMasterDetail
```

Клик уходит обычным table-level EVENT'ом, сервер снимает строку и отдаёт `notify` —
пользователь видит эталонный текст. У остальных ТЧ `allowAdd: false` из layout
по-прежнему означает структурный запрет и кнопку скрывает.

### 3.7 Границы

- Фронт **не** вычисляет правило: какой вычет «периодический» — доменное знание сервера.
- Фронт **не** конструирует и не разбирает команду; суффикс `:VychetyIPN` непрозрачен.
- Фронт **не** хардкодит и не переводит текст сообщения — он приходит в `notify`.
- Master-detail фильтр остаётся клиентским: `table.rowActivate` — про состояние
  зависимых узлов, а не про фильтрацию строк.
- `props.rowActivate` без `activate` в `actions` — баг композера; фронт молчит и команду
  не собирает.

## 5. Альтернативы и почему отклонены

**A1. Гасить/прятать «Добавить» по `allowAdd=false` (как просила входная спека §5).**
Отклонено владельцем: расходится с эталоном — в 1С кнопка активна и объясняет причину, а
скрытая кнопка не даёт пользователю понять, почему действие недоступно. Спека сама это
разрешает (§6: «если UI оставит „Добавить“ активной, данные всё равно не испортятся»).
Решение окончательное, в том числе как временная страховка на период доработок бэка.

**A2. `disabled` вместо скрытия + tooltip с причиной.** Disabled-кнопка не отдаёт клик,
причину пришлось бы вешать на обёртку — хак ради состояния, которое всё равно
объясняется сообщением сервера.

**A3. Показывать текст правила с клиента (хардкод или i18n-ключ).** Нарушает
server-driven дисциплину ADR-0011 §2.5: текст правила — доменное знание, он живёт там же,
где само правило.

**A4. Считать правило на клиенте по составу ТЧ.** То же нарушение, плюс дубль домена и
неизбежное расхождение с сервером при изменении справочника.

**A5. Реализовать в `table-node.tsx`.** Там нет ни состояния выбора, ни строк — §3.1.

**A6. Слать `activate` по двойному клику (как LIST).** Двойной клик в 1С — открытие
строки (`nav.rowOpen`), а правило переключается на одиночном выборе.

**A7. Отправлять «пробное» добавление без локальной вставки строки** (чтобы убрать
мигание). Требует нового метода в `use-table-sync` и всё равно тратит round-trip;
правильное лекарство — `addDeniedReason` пропом (задача 3 бэку), а не обход в `sync`.

## 6. Последствия

**Плюсы.** Механизм универсальный: любой ТЧ, которой в эталоне нужен
`ПриАктивизацииСтроки`, достаточно выдать `rowActivate` миграцией — правок фронта под
каждый новый документ не потребуется. Правило и его текст остаются в одном месте.

**Цена и известные дефекты (следствия §3.6, лечатся на бэке):**

1. **Строка мигает.** Добавление оптимистичное: строка появляется и исчезает ответом
   сервера. Уйдёт с задачей 3 (`addDeniedReason`).
2. **Ложный dirty.** Локальное добавление помечает форму изменённой, и после отказа
   флаг остаётся взведённым.
3. **Путь отказа стал штатным.** Пока сервер отвечает на отказ `setValue <ТЧ> []`,
   ошибочный клик стирает строки графика по другим вычетам. Смягчить на клиенте нечем:
   `setValue` по binding — canon, фронт обязан принять его как есть (ADR-0011).
   Блокирующая задача 1 бэку.
4. **Гонка ревизии.** `flushPendingTables: false` запрещает ждать in-flight table-EVENT,
   поэтому команда может уйти со старой ревизией и получить 409. Задача 2 бэку.

**Риск разрастания.** `showAdd` завязан на признак master-detail. Если появится detail-ТЧ
со структурным запретом добавления, ей понадобится явный признак от бэка (тот же
`addDeniedReason`/отдельный проп) — сегодня такого случая нет.
