# Задачи для бэкенда — `table.rowActivate` и отказ «Добавить» в ТЧ «График вычета»

Постановка по итогам реализации фронта по
[frontend-spec-table-row-activate.md](frontend-spec-table-row-activate.md)
(ADR-0013 §4.4, ADR-0022). Решения фронта зафиксированы в
[ADR-0014](ADR-0014-sdui-table-row-activate.md). Документ-прувпойнт —
«Регистрация заявлений по вычетам ИПН». Дата: 2026-07-30.

Фронт свою часть выложил: диспатч `activate` с дедупом по `rowId`, применение `setProp`
без спец-обработки. Одно поведение изменено против §5 фронт-спеки — по решению владельца
UI приведён к эталону 1С: **кнопка «Добавить» у detail-ТЧ не гаснет и не прячется**,
ошибку на клик рисует сервер (см. §0).

Решение окончательное: гашения кнопки не будет ни временно, ни как страховки на период
доработок бэка (ADR-0014 §5, альтернатива A1). Практическое следствие — **путь отказа
§3.4 стал штатным сценарием, а не аварийным**: в него попадает любой ошибочный клик
пользователя, и другого барьера перед ним в UI нет. Отсюда задача 1 и её приоритет.

---

## 0. Что делает фронт (контракт с его стороны)

| Момент | Что шлёт фронт |
|---|---|
| одиночный клик по строке / смена активной строки TABLE, у которой в `actions` есть `trigger: "activate"` | `COMMAND` с готовой командой бэка и `value: { "rowId": "<rowId строки>" }`, `behavior` — как прислал бэк |
| повторный клик по уже активной строке | ничего (дедуп по `rowId`; сбрасывается на `setValue` по binding таблицы) |
| клик «Добавить» в detail-ТЧ, когда сервер прислал `setProp allowAdd=false` | обычный table-level `EVENT` (`trigger: "change"`, `fullSnapshot: true`) с полным массивом строк, включая добавленную |

Фронт **не** вычисляет правило, **не** конструирует команду, **не** хардкодит текст
сообщения и **не** гасит кнопку по своим соображениям. Нет `activate` в `actions` —
клик по строке на сервер не ходит вовсе.

Пример запроса активации строки:

```json
{
  "formSessionId": "…",
  "revision": 7,
  "action": {
    "type": "COMMAND",
    "command": "table.rowActivate:VychetyIPN",
    "value": { "rowId": "r-42" }
  }
}
```

## Задача 1 — отказ по правилу не должен стирать ТЧ целиком (блокирующая)

**Что сейчас** (пример из §3.4 фронт-спеки): при добавлении строки графика в обход
правила сервер снимает её так:

```json
{
  "patches": [
    { "op": "setValue", "binding": "GrafikVycheta", "value": [] },
    { "op": "setValue", "binding": "GrafikVycheta.footer", "value": { "Razmer": 0 } }
  ],
  "effects": [{ "type": "notify", "level": "warning", "message": "Вид предоставления вычета … График ввести невозможно." }]
}
```

**Сначала — подтвердить факт.** По примеру нельзя понять, шлёт ли handler буквально
пустой массив всегда, или это «прежний массив без добавленной строки», который в примере
оказался пустым. Если верно второе — задача закрыта, достаточно ответить «шлём прежний
массив» и приложить ответ со стенда на документе с непустым графиком.

**Почему это важно.** `setValue` по binding таблицы для фронта — canon: он принимает
массив как есть, не мержит и не фильтрует (ADR-0011, «canon — только от сервера»),
смягчить на клиенте нечем. А `GrafikVycheta` хранит строки по ВСЕМ вычетам документа
(detail-ТЧ, ключ связи `VychetIPN`; master-detail фильтр — презентационный,
ADR-0013 §4.2). Поэтому если в ответе действительно `[]`, документ со сценарием
«периодический вычет с заполненным графиком + базовый вычет» теряет корректные строки
периодического вычета, как только пользователь нажмёт «Добавить» на базовом.

Раньше эта ветка была аварийной (кнопка гасла, дойти до неё можно было только в обход).
Теперь это штатный путь, и UI-барьера перед ним не будет (см. преамбулу) — цена ошибки
выросла, а страховать её можно только на сервере.

**Что сделать (если подтвердилось `[]`):** возвращать в `setValue GrafikVycheta`
**прежний массив строк без добавленной**, а не пустой; `footer` пересчитывать по этому
же массиву.

```json
{
  "patches": [
    { "op": "setValue", "binding": "GrafikVycheta", "value": [ { "rowId": "g-1", "VychetIPN": {…}, "Razmer": 12000, … } ] },
    { "op": "setValue", "binding": "GrafikVycheta.footer", "value": { "Razmer": 12000 } }
  ],
  "effects": [{ "type": "notify", "level": "warning", "message": "Вид предоставления вычета «Базовый налоговый вычет» не равен «По периодическим платежам». График ввести невозможно." }]
}
```

Текст сообщения — прежний, эталонный (сверен с 1С, скриншот в задаче). Уровень
`warning` фронт рисует тостом.

**Как проверить:** документ с двумя вычетами (периодический с 1 строкой графика +
базовый). Выбрать базовый вычет → «Добавить» в графике → тост с сообщением, строка
периодического вычета **на месте**, `footer` не обнулился.

## Задача 2 — ревизия на немутирующей `table.rowActivate`

**Что сейчас:** `behavior` у `activate` — все три `false`, в том числе
`flushPendingTables: false`, поэтому фронт по спеке **не ждёт** незавершённые
table-EVENT'ы перед отправкой команды. Возникает гонка:

1. пользователь правит ячейку ТЧ, уходит с неё → фронт шлёт `EVENT` с `revision: 7`;
2. тем же кликом он попадает в другую строку → фронт шлёт `COMMAND table.rowActivate`
   тоже с `revision: 7` (ответ на EVENT ещё не пришёл, ревизия не обновилась);
3. сервер к этому моменту обработал EVENT и поднял ревизию до 8 → команда получает
   409 `REVISION_CONFLICT`, пользователь видит диалог конфликта на ровном месте.

Обойти на фронте нечем: единственный механизм ожидания — это и есть
`flushPendingTables`, который спека запрещает (и правильно: клик по строке не должен
стоить flush'а незакоммиченного ввода).

**Что сделать (решение за бэком, нужен ответ):**
- либо не проверять `revision` для команд с `behavior.flushPendingTables === false`
  (немутирующие по контракту) — применять их к актуальному состоянию сессии и
  отвечать текущей ревизией;
- либо сериализовать запросы одной `formSessionId` и обрабатывать команду после
  уже принятого EVENT'а, не считая расхождение ревизии конфликтом.

Инвариант из §5 п.5 сохраняется: ответ на `table.rowActivate` ревизию **не поднимает**.

**Как проверить:** ввести значение в ячейку «Вычетов ИПН» и, не нажимая Enter, кликнуть
мышью по другой строке — ни 409, ни диалога конфликта, введённое значение не потеряно.

## Задача 3 — `addDeniedReason`: причина отказа пропом (не блокирующая, но желательная)

**Зачем:** сейчас, чтобы показать причину, фронт вынужден отправить заведомо
отвергаемое добавление — строка на мгновение появляется в таблице и исчезает ответом
сервера, документ помечается изменённым, тратится round-trip. В 1С строка не появляется
вовсе: «Добавить» сразу отвечает сообщением. Поскольку гашения кнопки не будет, это
единственный способ убрать лишний round-trip и мигание строки, не расходясь с эталоном.

**Что сделать:** рядом с существующим `setProp allowAdd` слать на тот же detail-узел
причину запрета:

```json
{
  "patches": [
    { "op": "setProp", "nodeId": "table.grafikVycheta", "key": "allowAdd", "value": false },
    { "op": "setProp", "nodeId": "table.grafikVycheta", "key": "addDeniedReason",
      "value": "Вид предоставления вычета «Базовый налоговый вычет» не равен «По периодическим платежам». График ввести невозможно." }
  ]
}
```

- правило разрешает добавление → `allowAdd: true` и `addDeniedReason: null`
  (проп обязательно сбрасывать, иначе фронт покажет протухшую причину);
- шлётся в тех же четырёх точках, где уже считается `allowAdd` (OPEN, изменение
  «Вычетов ИПН», смена физлица, `table.rowActivate`).

**Как это использует фронт:** пришёл `addDeniedReason` → «Добавить» остаётся активной,
клик показывает тост с этим текстом и строку не добавляет, запроса нет. Пропа нет —
поведение текущее (клик уходит на сервер, ответ по задаче 1). Текст целиком серверный,
фронт его не сочиняет и не переводит.

Правило на сервере остаётся авторитетным независимо от пропа: задача 1 никуда не
девается и продолжает страховать обход UI.

## Задача 4 — подтвердить, что композер реально отдаёт `activate` (проверка, не правка)

По §6 фронт-спеки: есть `props.rowActivate`, но в `actions` нет элемента с
`trigger: "activate"` — это баг композера, фронт команду сам не конструирует и клик по
строке молча остаётся клиентским.

**Как проверить:** в ответе OPEN документа «Регистрация заявлений по вычетам ИПН» у узла
`table.vychetyIPN` должно быть ровно два действия:

```json
"actions": [
  { "trigger": "change", "actionId": "fieldEvent" },
  { "trigger": "activate", "actionId": "command",
    "command": "table.rowActivate:VychetyIPN",
    "behavior": { "flushPendingTables": false, "resetsDirty": false, "closeAfter": false } }
]
```

и `props.rowActivate: true`. У прочих ТЧ (например «График платежей» в заявке ГП)
массив `actions` прежний — фронт по ним запросов не шлёт.

## Приоритеты

| # | Задача | Приоритет | Почему |
|---|---|---|---|
| 4 | подтвердить `activate` в `actions` | сначала | без него фронтовая часть просто не включается |
| 1 | отказ не стирает ТЧ целиком | блокирующая | потеря данных пользователя, UI-барьера нет |
| 2 | ревизия на немутирующей команде | высокая | ложный 409 при обычной работе с ТЧ |
| 3 | `addDeniedReason` | по возможности | убирает мигание строки, round-trip и ложный dirty |

Задачи 1 и 2 нужны для корректности; 3 — для UX-паритета с эталоном. Фронт готов к
любому порядку: без задачи 3 он работает по текущему контракту, без задач 1/2 —
работает, но с описанными дефектами.

## Границы

- Правило «какой вычет периодический» остаётся доменным знанием сервера. Фронт сообщает
  активную строку (`rowId`) и применяет патчи — своей копии правила у него нет и не будет.
- `rowId` в `value` — идентификатор строки из того же массива, что сервер прислал в
  `value` TABLE-узла. Суффикс кода ТЧ в команде (`:VychetyIPN`) фронт не разбирает и не
  собирает — он приходит готовым.
- Master-detail фильтр остаётся клиентским (ADR-0013 §4.2); `table.rowActivate` — про
  состояние зависимых узлов, а не про фильтрацию строк.
