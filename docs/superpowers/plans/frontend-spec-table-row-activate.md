# Frontend-спека: клик по строке ТЧ уходит на сервер (`table.rowActivate`)

Статус: спека для фронтендера (fin-web). Бэкенд-часть **реализована** в webbuh (аддитивно, уже в ветке).
Дата: 2026-07-29.

Основание: ADR-0013 §4.4 (отложенная опция серверной реакции на выбор строки master),
ADR-0022 (доменные команды ТЧ, префикс `table.`).
Связанные: `frontend-spec-complex-tables.md` (master-detail), `frontend-spec-action-behavior.md` (§A1
`behavior`), `frontend-spec-event-names.md` (§A2 «команда приходит готовой»).

---

## 1. Задача

Правило эталона в документе «Регистрация заявлений по вычетам ИПН»:

> График вычета вводится только вычету с `ВидПредоставленияВычета = По периодическим платежам`.
> Иначе 1С отказывает: *«Вид предоставления вычета "Базовый налоговый вычет" не равен
> ""По периодическим платежам"". График ввести невозможно.»*

В 1С за это отвечает `ВычетыИПНПриАктивизацииСтроки`: кнопка «Добавить» в ТЧ «График вычета»
отражает **текущую** строку ТЧ «Вычеты ИПН» и переключается при переходе между строками.

У нас выбор строки master живёт только на клиенте (ADR-0013 §4.2 — презентационный
master-detail-фильтр без round-trip), сервер про него не знает, и правило, зависящее от текущей
строки, выразить нечем. Эта спека закрывает ровно этот разрыв.

### 1.1 Что уже работает без правок фронта

Бэкенд закрыл всё, что можно было закрыть в одиночку. **Ничего из этого менять не нужно:**

| Момент | Что делает сервер |
|---|---|
| OPEN формы | считает доступность «Добавить» по составу «Вычетов ИПН» → `setProp allowAdd` |
| изменение ТЧ «Вычеты ИПН» | пересчитывает то же → `setProp allowAdd` |
| смена «Физического лица» | состав вычетов перезаписан → пересчитывает → `setProp allowAdd` |
| строка графика всё же добавлена в обход | снимает её: `setValue GrafikVycheta` + `notify` с текстом эталона |

Не хватает **одного** — реакции на клик по строке. До выката этой спеки поведение не
деградирует: на смешанном составе (базовый + периодический вычет) кнопка просто остаётся
активной, а ошибочно добавленную строку сервер снимет с объяснением.

## 2. Что теперь присылает бэк

У TABLE-узла `table.vychetyIPN` в `actions` появился **второй** элемент. Первый (`change`,
table-level sync по ADR-0011 §3.4) не меняется:

```json
{
  "id": "table.vychetyIPN",
  "type": "TABLE",
  "binding": "VychetyIPN",
  "props": {
    "editable": true,
    "allowAdd": true,
    "rowActivate": true,
    "label": "Вычеты ИПН"
  },
  "actions": [
    { "trigger": "change",   "actionId": "fieldEvent" },
    {
      "trigger": "activate",
      "actionId": "command",
      "command": "table.rowActivate:VychetyIPN",
      "behavior": { "flushPendingTables": false, "resetsDirty": false, "closeAfter": false }
    }
  ]
}
```

- `command` приходит **готовой строкой** — не конструируй и не разбирай её (§A2).
  Суффикс после `:` — код ТЧ, он нужен серверу, потому что COMMAND не несёт `sourceNodeId`.
- `behavior` — все три `false`: команда немутирующая, ревизию **не поднимает**.
  Клик по строке не должен стоить flush'а незакоммиченного ввода.
- Действие эмитится **точечно**: только у TABLE с `props.rowActivate === true`. У остальных ТЧ
  массив `actions` прежний — клик по строке на сервер не ходит.

## 3. Что менять на фронте

### 3.1 `table-node.tsx` — диспатчить активацию строки

При смене активной строки найти в `node.actions` элемент с `trigger === 'activate'` и, если он
есть, отправить его команду с `rowId` строки:

```ts
const activateAction = node.actions?.find(a => a.trigger === 'activate')
const lastActivatedRef = useRef<string | null>(null)

const handleRowActivate = (row: TableRow) => {
  if (!activateAction?.command) return
  if (lastActivatedRef.current === row.rowId) return   // дедуп, см. 3.2
  lastActivatedRef.current = row.rowId

  dispatch({
    type: 'COMMAND',
    command: activateAction.command,   // готовая строка от бэка
    value: { rowId: row.rowId },       // ключ именно rowId
    behavior: activateAction.behavior,
  })
}
```

**Когда звать.** Тот же момент, в который таблица уже сейчас публикует выбор для master-detail
фильтра (`<binding>.__selectedRowId`). Нового понятия «активная строка» вводить не нужно:
одиночный клик по строке и переход стрелками = `activate`. Двойной клик не нужен —
это не `nav.rowOpen`.

### 3.2 Дедуп по `rowId` — обязателен

Повторный клик по уже активной строке round-trip порождать не должен. Без дедупа каждый клик и
каждый ре-рендер с тем же выбором будут молотить запросы — при том что ответ идентичен.

Сбрасывать `lastActivatedRef` нужно, когда таблица получает новый массив строк
(`setValue` по её binding) — после этого прежний `rowId` мог исчезнуть.

### 3.3 Применение ответа — уже поддерживаемый путь

Ответ — обычные патчи. Здесь придёт `setProp` на **другой** узел (detail-таблицу):

```json
{
  "patches": [
    { "op": "setProp", "nodeId": "table.grafikVycheta", "key": "allowAdd", "value": false }
  ],
  "effects": []
}
```

Обрати внимание: `op` — camelCase (`setProp`), как у всех патчей.

Специальной обработки не требуется, но нужно убедиться, что **панель ТЧ перечитывает
`props.allowAdd` после патча** и кнопка «Добавить» перерисовывается (см. чек-лист §5, п. 6).
Если сегодня `allowAdd` читается один раз при монтировании — это надо поправить.

### 3.4 Отказ сервера — обычный `notify`

Если строка графика всё-таки добавлена в обход правила, сервер снимет её и объяснит причину:

```json
{
  "patches": [
    { "op": "setValue", "binding": "GrafikVycheta", "value": [] },
    { "op": "setValue", "binding": "GrafikVycheta.footer", "value": { "Razmer": 0 } }
  ],
  "effects": [
    {
      "type": "notify",
      "level": "warning",
      "message": "Вид предоставления вычета «Базовый налоговый вычет» не равен «По периодическим платежам». График ввести невозможно."
    }
  ]
}
```

Это существующий контракт (`setValue` строк + `notify`) — новой обработки не нужно. Важно лишь,
чтобы `setValue` по binding таблицы **разрешал in-flight состояние** `use-table-sync` (как и для
любого другого canon-ответа), иначе таблица зависнет в pending.

## 4. Чего делать НЕ нужно

- **Не** вычислять правило на клиенте. Какой вычет «периодический» — доменное знание справочника,
  оно остаётся на сервере. Фронт сообщает, какая строка активна, и применяет патч.
- **Не** вешать `activate` на все таблицы «на всякий случай». Клик по строке — самая частая
  операция в таблице; ориентир строго `props.rowActivate === true`.
- **Не** трогать master-detail фильтр: он остаётся клиентским и работает как раньше.
  `table.rowActivate` — про состояние зависимых узлов, а не про фильтрацию строк.
- **Не** гасить кнопку самостоятельно «до ответа сервера». Оптимистичное состояние тут вредно:
  правило знает только сервер, а мигание кнопки на каждом клике хуже, чем задержка в один ответ.

## 5. Как проверить

Документ: «Регистрация заявлений по вычетам ИПН», две строки в «Вычетах ИПН» — базовый
налоговый вычет и вычет по периодическим платежам.

1. Кликнуть строку с **базовым** вычетом → «Добавить» в «Графике вычета» становится неактивной
   (пришёл `setProp allowAdd=false`).
2. Кликнуть строку с **периодическим** вычетом → «Добавить» снова активна.
3. Повторный клик по той же строке → в Network **нет** нового запроса (дедуп, §3.2).
4. Ввести значение в ячейку ТЧ, не коммитя, и кликнуть по строке → **ввод не потерян**
   (команда немутирующая, flush не делает).
5. `revision` в ответе на `table.rowActivate` **не увеличилась** относительно предыдущей.
6. Кнопка действительно перерисовалась, а не только изменился prop в стейте (§3.3).
7. У любой другой ТЧ (например «График платежей» в заявке ГП) клик по строке запросов не шлёт.
8. Новый документ, «Вычеты ИПН» пусты → «Добавить» в графике неактивна с первого кадра,
   до записи документа.

## 6. Границы / вопрос к бэку

- Есть `props.rowActivate`, но в `actions` нет `activate` — это баг бэка, не повод
  конструировать команду самому. Пиши — поправим композер.
- Состояние кнопки **до** первого клика бэк считает по составу ТЧ и намеренно делает
  разрешающим (есть хоть один периодический вычет ⇒ активна). Это осознанный выбор: блокировать
  работу по составу нельзя, а ошибочное добавление всё равно перехватит сервер (§3.4).
- Правило авторитетно на сервере независимо от состояния кнопки. Если UI по какой-то причине
  оставит «Добавить» активной, данные всё равно не испортятся.
- Механизм универсальный: любой ТЧ, которой в эталоне нужен `ПриАктивизацииСтроки`, достаточно
  выдать скаляр `rowActivate` миграцией — правок фронта под каждый новый документ не потребуется.
