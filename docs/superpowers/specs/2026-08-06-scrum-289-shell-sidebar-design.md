# SCRUM-289 «Перенос Shell в SDUI», фаза 1 — server-driven сайдбар

Дата: 2026-08-06. Статус: дизайн одобрен, готов к плану.
Задача 7 эпика SCRUM-258. Спеки-первоисточники: `specs-local/scrum-289-perenos-shell-v-sdui/`
(`frontend-spec-shell.md` от 16.07 + `backend-answers-SCRUM-289-shell.md` от 06.08).

## Контекст и границы

SDUI сейчас управляет только содержимым страницы; оболочка (Sidebar, TopBar, Workspace) —
статичные фронт-компоненты. Цель фазы 1 — **сделать сайдбар server-driven**: пункты, порядок,
метки (RU/KZ по языку сессии), иконки и маршруты приходят от бэка деревом `APP_SHELL`.

**Композиция (подтверждена бэком 06.08):** OPEN оболочки отдаёт дерево
`APP_SHELL → TOP_BAR (пустой) + SIDEBAR (LINK-узлы) + WORKSPACE (пустой)`. Сайдбар приходит
**один раз** (не дублируется в ответах `/modules/X` и документов). Навигация по `LINK` —
**клиентская** по `props.route`; у `LINK` **нет `actions`** (осознанно — сервер в переходе
не участвует).

**Вне фазы 1:** наполнение `TOP_BAR`/`WORKSPACE` (фаза 2); снос статичного layout, 14 URL-регексов
`resolve-page-type.ts`, рендер контента внутри `WORKSPACE` через единый роут (задача 8/9); роли/
персонализация меню (нужна авторизация).

## Блокер и его снятие

dev-api (`dev-api.qazyna.ai`) на момент дизайна отдаёт старый контракт: `layoutCode:"APP_SHELL"`→404,
`route:"/"` без layoutCode→400. Причина (ответ бэка): единый роутинг был только в ветке `sdui-1.5`,
сейчас вливается в `main`. После выкатки заработают оба варианта. Отдельной песочницы нет — e2e
после деплоя. **Следствие для дизайна:** пре-прод фронт должен работать без регресса даже при 404
на `APP_SHELL` → app-level фолбэк на легаси-сайдбар (см. §4).

## Ключевое решение: коллизия типа `LINK`

Спека §3.1 (от 16.07) предлагала завести новый `LinkNode`, считая `LINK` неотрендеренным. С тех пор
generic `LinkNode` уже существует (`ui/nodes/action/link-node.tsx`: `props.text` + серверный
navigate через `actions`). Бэк шлёт пункты сайдбара **тоже** как `type:"LINK"`, но с
`props.label/icon/route` и **без `actions`**. Один тип — два разных представления.

**Решение:** `SidebarNode` сам рендерит свои `LINK`-дети как пункты меню (не делегирует их
generic-`LinkNode` через реестр). Новый `LinkNode` не заводим. Это устраняет коллизию, не трогает
generic-линк и всё равно наполняет `SidebarNode` настоящим рендерером (критерий §6.3). Это
осознанное отклонение от §3.1 устаревшей спеки.

## Архитектура (вариант «только сайдбар в текущем Layout»)

Подтверждён паттерном SCRUM-291: реальное заполнение SDUI-нод + props-driven (фронт перестаёт
строить `/modules/${code}`, берёт `props.route` готовым) + всё безопасно до флипа.

```
Layout
 ├─ <ShellSidebarHost fallback={<Sidebar/>} />   ← НОВОЕ (SDUI-хост)
 ├─ <TopBar/>            (без изменений)
 ├─ <main> AppRoutes     (без изменений)
 └─ <WorkspaceTabBar/>   (без изменений)
```

### Компоненты

**`ShellSidebarHost`** (`features/sdui`, монтируется в `Layout` вместо `<Sidebar/>`).

- `useQuery(['app-shell', language])` → `viewTransport.post({ type:'OPEN', layoutCode:'APP_SHELL' })`.
  Загрузка **один раз**, изолирована от route-driven tree-store контента (свой запрос, не dispatch/
  tree-store — чтобы не коллизить с content-экранами). Ре-фетч на смене языка (ключ включает язык;
  метки RU/KZ фиксируются на OPEN).
- Из ответа берёт поддерево `SIDEBAR` и рендерит через `NodeRenderer` (реестр → живой `SidebarNode`).
- `isLoading`/`isError` → отдаёт фолбэк (реализация фолбэка — в `App.tsx`, см. §4).
- Сессия SDUI не нужна: `SidebarNode`/пункты читают только `props` + router (у дерева пустой `state`).

**`SidebarNode`** (заполняем заглушку `ui/nodes/shell/sidebar-node.tsx`).

- Хром сайдбара (лого, имя приложения `sidebar.appName` — клиентский i18n, кнопка сворачивания) —
  стиль из существующего `widgets/sidebar/ui/sidebar.tsx`.
- Маппит `node.children` (LINK-узлы) в пункты меню (внутренний под-компонент `SidebarLinkItem`):
  иконка (резолвер §резолвер) + `props.label`; активность — совпадение `props.route` с
  `location.pathname` (`/` точно, остальное `startsWith`); клик → `navigate(props.route)`.
- Свёрнутость: `props.collapsed` — стартовое значение; дальше клиентский тоггл + localStorage
  (как сейчас). Открытый вопрос «клиент vs сервер» в фазе 1 не решаем.

**Резолвер иконки** (новый, в SDUI): имя→SVG-компонент. Имена от бэка: `home, bank, warehouse,
actives, salary, admin, reports` → ассеты из `shared/assets/navigation`. Неизвестное имя → fallback.
Существующие `button-icons.tsx`/`icon-node.tsx` (две несовместимые карты, отмеченные бэком) **не
трогаем** — консолидация вне скоупа 289 (follow-up).

**`AppShellNode`/`TopBarNode`/`WorkspaceNode`** — остаются заглушками (нужны в задаче 9). В фазе 1
не рендерятся: хост выдёргивает только `SIDEBAR`.

## §4. Фолбэк и безопасность

При `isLoading`/`isError` OPEN `APP_SHELL` (бэк ещё не готов на среде) `App.tsx` рендерит легаси
`<Sidebar/>` — регресса нет. Изоляция соблюдена: `ShellSidebarHost` (SDUI) не импортит легаси;
фолбэк собирается проводом в `App.tsx` (композиционный корень — там уже подключены оба мира через
gateway'и). Легаси-сайдбар (`widgets/sidebar`, `use-sidebar`, `fetch-navigation-items`,
`navigation-items` как источник) удаляем **отдельным коммитом после прод-верификации**.
`/api/settings/modules` **не удаляем** — эндпоинт нужен `entities/module/use-resolve-type-page-code`
(резолв type→pageCode для редиректов).

## §5. Что не меняется

TopBar, `WorkspaceTabBar`, `AppRoutes`/контент, все роуты, 14 регексов `resolve-page-type.ts`.
Переходы идут по существующим роутам (`/modules/<code>` и т.д.) — их приносит `props.route` с бэка.

## §6. Тестируемость

- Unit: `SidebarNode` (рендер пунктов из фикстуры, активный пункт по pathname), резолвер иконок
  (известные имена + fallback), `ShellSidebarHost` (loading/error → фолбэк).
- Разработка против контракта на локальной фикстуре ответа `APP_SHELL`.
- E2E — после выкатки бэка на среду (проверяет автор таски). Фолбэк гарантирует отсутствие регресса
  до этого.

## §7. Критерии приёмки (из спеки §6)

1. Меню строится из server-дерева: пункты, порядок, метки (по языку), иконки, переходы — всё из
   ответа; в коде фронта нет построения `/modules/${code}` и вызова `GET /api/settings/modules` на
   пути SDUI-сайдбара.
2. Клик по пункту → переход по `props.route` (router).
3. `SidebarNode` заполнен и используется движком; неизвестное имя иконки → fallback.
4. Смена языка → метки меню на нужном языке при следующем OPEN.
5. TopBar/Workspace работают как раньше — регресса нет (в т.ч. при недоступном бэке — фолбэк).
