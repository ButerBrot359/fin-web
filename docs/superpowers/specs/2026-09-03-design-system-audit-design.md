# Дизайн-система fin-web: токен-слой, аудит против Figma, скриншотная регрессия

Дата: 2026-09-03. Статус: утверждён владельцем (чат-сессия 03.09).
Ветка работ: `feature/design-system`. Охват: **SDUI + общий каркас**
(shell, workspace-вкладки, `shared/ui`, SDUI-ноды); легаси-экраны руками не
полируются — они под снос, но общий токен-слой подтянет их автоматически там,
где они читают те же Tailwind-классы и MUI-тему.

## 0. Проблема

Интерфейс визуально разъехался с утверждёнными макетами
(Figma: `8RxAFhNubquQ1bz912H2wB`, страница «design»). Причины, установленные
разведкой 03.09:

1. **Два несинхронизированных источника правды.** Палитра объявлена в
   `tailwind.config.ts` (`ui-01…08`, `accent`, `support`), и та же палитра
   продублирована literal-hex'ами в MUI-теме
   (`src/app/theme/theme.ts`, 295 строк: `#2a75f4` ×24, `#222124` ×20 и т.д.).
2. **Дрейф мимо токенов.** ~174 hex-вхождения в 29 файлах `src/`;
   среди ~25 уникальных цветов — «левые», отсутствующие и в Figma, и в
   палитре: `#d9d9d9`, `#e5e7eb` (дефолтный tailwind-серый), `#eceff4`,
   `#e6e9ee`, `#dcdcdc`, россыпь жёлтых. Интерфейс фактически собран из трёх
   палитр.
3. **Нет шкалы отступов/гэпов** — в tailwind заданы только радиусы и четыре
   шрифта; spacing каждый компонент выбирает на глаз.
4. **Нет визуальной регрессии** — ни один из пунктов выше не ловится тестами.

При этом дизайн-система в Figma существует и формализована переменными:
`UI 01…06`, `Accent 01/Accent 01` (+hover/pressed в макетах кнопок),
`Accent 02`, шрифтовые `H2` (Google Sans Bold 26), `Body 1` (Medium 16),
`Body 2` (Medium 14). Наша tailwind-палитра им соответствует — проблема не в
отсутствии токенов, а в дисциплине их использования.

## 1. Токен-слой (ядро)

### 1.1 Канон: `src/shared/design/tokens.ts`

Единственное место в кодовой базе, где существуют literal-значения дизайна.
Структура токена: `{ cssVar: string; value: string }`; модуль экспортирует
группы и хелпер `cssVar(token)` → `var(--ui-01, #ffffff)`.

Состав:

- **Палитра (сырье, имена = переменным Figma):** `ui-01…08`,
  `accent-01` / `accent-01-hover` / `accent-01-pressed`, `accent-02`,
  `support-01`.
- **Семантические алиасы (ими пользуется код):** `text-primary` (ui-06),
  `text-secondary` (ui-05), `divider` (ui-03), `zebra` (ui-02),
  `header-line` (ui-06), `surface` (ui-01), `surface-raised` (ui-02),
  `selection` (ui-04), `primary` (accent-02), `error` (support-01),
  `brand` (accent-01). Список пополняется в Ф1 по фактическим употреблениям.
- **Типографика:** `h2` 26/700, `h3` 20/700, `body1` 16/500, `body2` 14/500,
  `caption` 12/500; семейство `'Google Sans', system-ui, sans-serif`.
- **Радиусы:** 4 / 8 / 12.
- **Spacing-шкала:** кратная 4 (4, 8, 12, 16, 20, 24, 32) — для gap/padding
  контейнеров и компонентов.
- **Тени:** `primary-hover`, `secondary-hover` (из tailwind), `popup`
  (`0 3px 24px rgba(42,117,244,.4)` — сейчас захардкожена в теме дважды).

### 1.2 Транспорт: CSS-переменные

- `injectDesignTokens()` — вызывается при старте приложения (в `main.tsx`),
  создаёт `<style>` с `:root { --ui-01: #ffffff; … }` из канона. Никаких
  билд-генераторов.
- `tailwind.config.ts` импортирует токены; каждое значение — `var()`-строка с
  фолбэком (`'01': 'var(--ui-01, #ffffff)'`). Ограничение tailwind:
  модификаторы прозрачности (`bg-ui-06/50`) с `var()` не работают — в
  кодовой базе не используются, страж (1.4) запрещает их появление.
- `src/app/theme/theme.ts` переписывается: все hex → `cssVar(...)`
  (MUI принимает CSS-строки везде, где сейчас literal).

### 1.3 Переезд существующего кода

Все ~174 hex-вхождения в 29 файлах заменяются на токены (класс tailwind или
`cssVar()`), с двумя исключениями:

- **значения с провода** — `textColor`/`background` из props SDUI-нод
  (`table-text-color`, `column-background`, appearance-правила) — это данные
  бэка, не стиль фронта; не трогаем;
- **«левые» цвета фронта** (`#d9d9d9`, `#e5e7eb`, `#eceff4`, жёлтые, …) —
  каждый мэпится на ближайший токен Figma; если у цвета есть осмысленная
  роль без токена (напр. warning-жёлтый из секции «Ошибки» Figma) — токен
  заводится осознанно со ссылкой на макет, а не копированием случайного hex.

### 1.4 Страж дрейфа

Vitest-тест (`src/shared/design/no-hex-drift.test.ts`) грепает `src/` на
hex-литералы и opacity-модификаторы tailwind-цветов:

- разрешены: `tokens.ts`, `*.test.*`, фикстуры скриншот-тестов;
- падение теста = появился хардкод мимо токенов.

## 2. Аудит против Figma

### 2.1 Источники

- Секция **Components** (`61:2023`) — компонентная библиотека макетов;
- опорные экраны: «Журнал проводок» (`466:15058`), «Справочники»
  (`322:13219`), «Приходно-кассовый ордер» (`170:6241`), «Главное меню»
  (`175:8796`), «Авторизация» (`545:22859`), «Ошибки» (`1014:25346`).

### 2.2 Метод

По компонентным группам — кнопки, поля ввода (filled-инпут, автокомплит,
дата), чекбоксы, вкладки формы, workspace-вкладки, таблицы (шапка, строки,
зебра), тулбары ТЧ, диалоги/поповеры, тосты, shell (сайдбар, топбар):

1. вытащить спеку группы из Figma (design-context узла + пипетка по PNG);
2. снять тот же компонент на стенде (Playwright, localhost против dev-api);
3. зафиксировать расхождения: цвет / отступ / радиус / размер / шрифт /
   состояние (hover, focus, error, disabled).

### 2.3 Артефакт

`docs/superpowers/specs/design-audit-checklist.md` (дата — в заголовке файла): таблица
«группа → расхождение → токен/значение по Figma → приоритет». Это бэклог
Ф4 — фиксов пачками.

## 3. Скриншотная регрессия

### 3.1 Инфраструктура

- `@playwright/test` в devDependencies; `playwright.config.ts`
  (`webServer: vite preview` на фиксированном порту, viewport 1440×900,
  анимации отключены, дата заморожена init-скриптом).
- Шрифт: локальный woff2 Google Sans (weights 500/700) в фикстурах тестов,
  сеть в тестах закрыта от CDN — иначе рендер недетерминирован.

### 3.2 Фикстуры

JSON-ответы `/api/view` (и смежных API), снятые с dev-api и закоммиченные в
`tests/visual/fixtures/`. `page.route` мокает сеть целиком. Представительные
экраны:

1. шелл + страница модуля;
2. карточка документа с ТЧ (включая VERTICAL-группы — «Отпуск»);
3. список документов;
4. табель-матрица;
5. отчёт TREE (ОСВ);
6. отчёт LEDGER (Карточка счёта);
7. карточка справочника;
8. диалог «Сохранить изменения?» и поповер автокомплита.

### 3.3 Соглашения

- Эталоны в git; рендер — **macOS** (закреплено соглашением; линукс-эталоны
  появятся вместе с CI, которого сейчас нет).
- `toHaveScreenshot` с `maxDiffPixelRatio: 0.001`.
- Скрипты: `npm run test:visual`, `npm run test:visual:update`.
- Запуск — обязательная часть стандартного цикла перед мержем в dev
  (наравне с `npm run build`).

## 4. Закладки фазы 2 (контракты, в этой таске НЕ реализуются)

### 4.1 Server-driven тема — `/api/theme`

Мотивация: SDUI-философия + желание владельца настраивать вид через UI
(аналог гибкости 1С). Контракт:

```jsonc
GET /api/theme
{ "tokens": { "ui-01": "#ffffff", "accent-02": "#2a75f4", … } }
```

Фронт на старте (после `injectDesignTokens`) накатывает полученные пары через
`setProperty` на `:root`. Неизвестные ключи игнорируются, отсутствующие
остаются дефолтами — старый бэк и офлайн не ломают ничего. Благодаря §1
это ~30 строк фронта и ноль правок компонентов. Admin-UI настройки — той же
фазой 2, отдельная таска с бэком.

### 4.2 «Изменить форму» (аналог 1С «Ещё → Изменить форму»)

Пер-форменные настройки (ширина инпута, видимость поля, положение блока,
прижатие к низу) — по архитектуре SDUI это **серверная** компоновка: бэк
хранит пер-пользовательские override'ы и патчит ими props дерева перед
отдачей `/api/view`. Фронт уже рендерит то, что прислали; для фазы 2 ему
нужен только диалог настройки, шлющий override'ы.

Обязательство ЭТОЙ таски — «фронт уважает layout-props с провода»:
аудит (§2) инвентаризирует props, которые фронт обязан читать
(width/flex колонок, gap/direction контейнеров, visible/enabled, прижатие
подвала), и помечает места, где фронт сегодня перебивает их хардкодом; такие
места чинятся в Ф4 как обычные расхождения.

## 6. Риски

- **tailwind + var():** прозрачностные модификаторы не работают — запрещены
  стражем; фолбэки в `var()` сохраняют рендер даже до `injectDesignTokens`.
- **Ф1 «bit-perfect»:** гарантируется ручной сверкой скриншотов до/после в
  рамках самой Ф1 (Ф2-инфры ещё нет); любые намеренные визуальные изменения
  в Ф1 запрещены.
- **macOS-эталоны:** скриншот-тесты не гоняются на других ОС до появления CI;
  фиксируем в README тестов.
- **Параллельные агентские ветки** активно мержатся в main — пофазный мерж и
  свежий rebase перед каждым PR обязательны.
