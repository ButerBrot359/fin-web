# Конструктор дизайна: архитектура и фронт-часть (v1)

Дата: 2026-09-10. Статус: согласовано с владельцем (стратегическая сессия).

## 0. Картина целиком

Конструктор дизайна — не один продукт, а **три двери в одну комнату**.
Комната — пер-пользовательские патчи дизайна, которые хранит и накладывает
бэк. Двери — способы эти патчи редактировать:

| Дверь                                   | Кто                | Что редактирует               | Фаза               |
| --------------------------------------- | ------------------ | ----------------------------- | ------------------ |
| **ИИ-помощник** («сделай панель шире»)  | Любой пользователь | Патч своей формы / своей темы | 2                  |
| **Диалог «Изменить форму»** (аналог 1С) | Любой пользователь | То же, руками и точно         | 4                  |
| **Админ-конструктор форм**              | Аналитик           | Базовый конфиг формы для всех | 5, отдельная спека |

Принципы (наследуются из спеки 04.09):

1. **Патчи накладывает бэк** до отдачи `/api/view` (и `/api/theme`). Фронт
   рендерит присланное и не знает, что дерево «патченное». Клиентского
   слияния нет — настройки переезжают между устройствами, бэк всё видит.
2. **Один словарь.** Редактируемые пропы — ровно словарь v1 (`visible`,
   `width`, `size`, `pinBottom`, `gap`, …). Конструктор не добавляет
   новых понятий — только UI над существующими.
3. **Деградация.** Патч не может сломать рендер: неизвестная нода молча
   пропускается, кривое значение клампится, неизвестный проп отбрасывается.
4. **Тема — тоже пер-пользовательская** (решение владельца 10.09): бэк
   хранит переопределения токенов на пользователя и отдаёт слитое с
   дефолтом. Дизайн-константы по-прежнему живут во фронтовом реестре
   `tokens.ts` — бэк хранит только override'ы значений.

## 1. Контракты

### 1.1 Патч формы (сердце системы)

```
GET    /api/view-settings/{screenKey}   → { "patch": [{ "nodeId": "field.org", "props": { "visible": false } }] }
PUT    /api/view-settings/{screenKey}   ← то же тело; ПОЛНАЯ ЗАМЕНА патча
DELETE /api/view-settings/{screenKey}   → сброс к дефолту
```

- `screenKey` — стабильный канонический ключ экрана (владеет бэк, он же
  резолвит его из роута `/api/view`). Фронт получает его в ответе
  `/api/view` (мета) и никогда не конструирует сам.
- **Полная замена, не дельты.** Undo тривиален: перед PUT'ом клиент (диалог
  или агент) помнит прежний массив — откат = PUT прежнего. Истории версий
  на бэке не нужно.
- `nodeId` — стабильные id нод дерева (`layout_nodes.node_code`), они уже
  в контракте `ViewNodeDto.id`.
- **`visible`/`enabled` в патче — только `false`** (сервер отвергает `true`):
  патч пользователя ограничивает представление, но не раскрывает скрытое по
  правам. «Показать обратно» = убрать запись из патча (полная замена это
  покрывает).

### 1.2 Тема

```
GET    /api/theme            → { "tokens": { "accent-02": "#2a75f4", … } }  // дефолт + override текущего пользователя
GET    /api/theme-settings   → только override'ы пользователя
PUT    /api/theme-settings   ← полная замена
DELETE /api/theme-settings   → сброс
```

Фронт накатывает пары из `/api/theme` на `:root` после `injectDesignTokens`.
Неизвестный токен игнорируется, кривое значение отбрасывает сам CSS —
валидация значений на бэке не нужна, реестр токенов бэку не нужен.

### 1.3 ИИ-помощник

Агент — ещё один клиент того же патч-API, серверными инструментами
(оркестрация уже на бэке, `/api/ai-assistant/ask`):

- `get_form_layout(screenKey)` — дерево нод (id, тип, label) для поиска цели;
- `apply_form_patch(screenKey, patch)` / `reset_form_settings(screenKey)`;
- `apply_theme_patch(tokens)` / `reset_theme()`.

UX: **применяет сразу, без превью** (решение владельца 10.09); «верни как
было» — агент держит прежний патч в разговоре и PUT'ит его обратно.
Контекст «на каком я экране» панель помощника уже передаёт.

> Статус (10.09): серверной оркестрации помощника в репо webbuh НЕТ
> (`/api/ai-assistant/*` живёт вне его) — инструменты агента отложены до
> появления этого бэка. Фронт-половина Ф2 (флаги + рефетч) реализована и
> заработает автоматически, когда бэк начнёт слать флаги.

## 2. Фронт-часть по фазам

Фаза 1 (бэк-хранилище и наложение) фронта не касается — всё ниже.

### Ф2 — эффект «настройки вида изменились»

Ответ `/ask` получает флаги `viewSettingsChanged` / `themeChanged`
(или эффект в общем реестре эффектов). Реакция фронта:

- `viewSettingsChanged` → инвалидация query текущего `/api/view` → форма
  перерисовывается уже патченной;
- `themeChanged` → рефетч `/api/theme` → повторный прогон применителя
  токенов на `:root`.

Объём: хук в `features/ai-assistant` + применитель темы (~30 строк) в
`app/` рядом с `injectDesignTokens`. Новых компонентов нет.

### Ф3 — тема при старте

После логина — `GET /api/theme`, накатить на `:root`. Эндпоинт недоступен /
офлайн → дефолты `tokens.ts`, приложение не замечает.

Реализовано (10.09 вечером) поверх этого:

- **UI темы** — «Меню пользователя → Тема оформления»
  (`features/theme-settings`): кураторский поднабор токенов (акцент, кнопки,
  два фона) color-пикерами; значения, равные дефолту реестра, не хранятся.
- **Масштаб интерфейса** («размер шрифтов», запрос владельца) — специальный
  ключ `ui-scale` в тех же theme-settings: применитель ставит `zoom` на
  корень (кламп 0.8–1.5), ступени 90/100/110/125%. Токеном-CSS-переменной
  это не сделать: раскладка почти вся в px, честное укрупнение шрифтов —
  вместе с контейнерами.
- **Экспорт/импорт темы** JSON-файлом — зеркало экспорта настроек формы.

### Ф4 — диалог «Изменить форму» (реализовано 10.09, v1)

Generic-диалог (не знает конкретных форм). Реализация v1:

- Пункт «Ещё → Изменить форму» приходит С БЭКА обычной MENU_ITEM-нодой
  (`CommandBarComposer.buildStandardMoreChildren`); команда
  `view.customizeForm` — ЕДИНСТВЕННАЯ клиентская команда контракта, dispatch
  перехватывает её до транспорта (контрактная константа, не разбор имён).
- `screenKey` приезжает в ответе OPEN → `tree-store`; диалог строит список
  нод по дереву с провода (поля/группы/таблицы с подписью; кнопки и меню не
  предлагаются — это команды и права, не представление).
- v2 диалога (реализовано 10.09 вечером, запрос владельца): ПОРЯДОК среди
  соседей одного родителя (стрелки ↑↓; проп `order`, бэк стабильно сортирует
  детей, непереставленные соседи держат свои места), ШИРИНА полей (px,
  пусто = авто; рендер уважает `width` нод-полей в обоих стеках) и
  ЭКСПОРТ/ИМПОРТ настроек JSON-файлом (чисто клиентские поверх готового
  API — бэку ничего не понадобилось). Записи чужих пропов при сохранении
  не теряются; `pinBottom` руками — v3, агент умеет через патч уже сейчас.
- Скрытые СЕРВЕРОМ ноды в списке не показываются — раскрыть их нельзя.
- После сохранения — шина «настройки вида изменились» → re-OPEN формы
  (грязную форму не переоткрываем: правки дороже свежей раскладки).

### Ф5 — админ-конструктор

Структурный редактор базового конфига (дерево + операции, живой превью тем
же SDUI-рендерером; drag-n-drop — не в первой версии). Отдельная спека,
когда дойдём.

## 3. Что фронт обязан НЕ делать

- Не сливать патчи на клиенте (единственное исключение обсуждалось для
  превью в диалоге и отвергнуто вместе с превью-режимом агента).
- Не хардкодить `screenKey` и списки нод — всё приходит с провода.
- Не давать агенту/диалогу пропов вне словаря v1 — расширение словаря
  это правка спеки 04.09, не конструктора.

## 4. Тесты

- Юниты применителя темы (мерж, неизвестный токен, повторный прогон).
- Юниты реакции на эффекты (`viewSettingsChanged` → инвалидация).
- Диалог (Ф4): юниты на сборку патча из дерева; e2e на дев-стенде —
  скрыть поле, увидеть результат, сбросить.
- Визуальная регрессия: эталоны снимаются с ДЕФОЛТНОЙ темы и без патчей;
  патченные состояния эталонами не фиксируем.
