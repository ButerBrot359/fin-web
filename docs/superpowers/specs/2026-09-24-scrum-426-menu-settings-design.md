# SCRUM-426: Конструктор меню — настройка бокового меню и разделов модулей

Дата: 2026-09-24. Статус: дизайн утверждён пользователем (сессия 24.09), реализация в ветках
`feature/SCRUM-426-menu-settings` обеих реп (fin-web + webbuh), от свежего `main`.

## 1. Цель и рамки

Администратор (и любой обладатель нового права «Настройка меню») настраивает **состав и
порядок** пунктов бокового меню и разделов внутри модулей: глобально, для ролей и для
конкретных пользователей. Любой пользователь подстраивает меню под себя, не ломая настроек
администратора. Настройка меню — **только отображение**, не права доступа: пункт, на который
у пользователя нет прав, не отображается ни при каких настройках; показ пункта прав не даёт.

Настраиваемые сущности (три уровня гранулярности), для каждой — скрытие и порядок:

- модули сайдбара (Банк и касса, Склад, …);
- секции внутри страницы модуля (Финансирование, Банк, Касса, …);
- отдельные ссылки внутри секций (Авансовый отчет, Кассы, …).

**Вне объёма v1:** переименование пунктов, перенос ссылок между секциями, кастомные секции,
ИИ-дверь.

**Пресеты «поделиться конфигурацией» (в объёме, решение владельца 25.09):** любой
пользователь публикует свой набор настроек меню под именем
(`menu_settings_presets`: имя+автор уникальны, роли автора замораживаются при
публикации); каталог виден по пересечению ролей автора и смотрящего (свои и для
админа — всегда); применение пресета = обычный PUT его патча в ЛИЧНЫЙ слой
применившего (отдельного apply-эндпоинта нет); удаление — автор или админ. REST:
`POST/GET /api/menu-settings/presets`, `GET/DELETE /api/menu-settings/presets/{id}`.
UI: кнопки «Поделиться» (публикация текущего черновика) и «Пресеты» (каталог) на
вкладке «Настройка модулей».

Образец архитектуры — конструктор дизайна (SCRUM-237): слои хранятся и мержатся на бэке,
фронт рендерит готовое дерево и не мержит патчи сам
(см. `2026-09-10-design-constructor-architecture-design.md`).

## 2. Текущее состояние (входные факты)

- Сайдбар: SDUI-нода `SIDEBAR` из `POST /api/view` (`APP_SHELL`), собирается
  `ShellComposer.buildNavLinks()` из захардкоженного `ModuleNavigationService` (webbuh).
  Легаси-фолбэк фронта — `GET /api/settings/modules`.
- Страница модуля: SDUI OPEN по роуту `/modules/{code}`; состав секций — таблица
  `module_items_settings` (JSON на модуль, сид из `kbp-menu/…/core-modules.json`) +
  `ModuleContributor`-ы (Отчёты, Аналитика). Легаси-фолбэк — `GET /api/settings/modules/{code}`.
- Меню сегодня **не фильтруется по правам**: все модули отдаются всем.
- У секций **нет кодов** (только nameRu/nameKz) — стабильные ключи для патчей отсутствуют.
- Права: `RightKind` (enum) + `role_permissions`; в проде — EAV-модель
  (`UserFullRightsResolver`, профили групп доступа → роли). Эндпоинта «мои права» нет.
- Конструктор дизайна: пакет `kz.asiaservis.viewsettings`, таблицы
  `user/default/profile_view_settings`, применение через `UserViewSettingsAdvice` на
  `/api/view`; фронт — customize-dialog + админ-реестр `src/pages/admin/design-constructor/`.

## 3. Бэкенд (webbuh)

### 3.1 Коды секций (предпосылка)

`ModuleItemDto` получает поле `code`. Миграция данных не нужна: код вычисляется на чтении
в `ModuleItemsSettingsService` — детерминированный слаг из nameRu (транслитерация,
уникальность в рамках модуля, при коллизии суффикс `-N`); JSON-сид может задать код явно,
тогда он сохраняется. Контрибьюторы (ReportAlt, Analytics) получают коды тем же
пост-процессингом. Переименование секции меняет код — осиротевший ключ патча просто
перестаёт находить пункт (безвредно).

### 3.2 Хранение: пакет `kz.asiaservis.menusettings`

Три таблицы по образцу viewsettings (идемпотентные миграции):

| Таблица                 | Ключ                                            | Слой                  |
| ----------------------- | ----------------------------------------------- | --------------------- |
| `default_menu_settings` | singleton (одна запись)                         | глобальный «для всех» |
| `profile_menu_settings` | `profile_key` (элемент «Профили групп доступа») | слой роли             |
| `user_menu_settings`    | `user_entry_id`                                 | слой пользователя     |

Слой пользователя один: его правит сам пользователь или обладатель права за него —
отдельного «админ-для-пользователя» слоя нет.

Патч слоя — JSON `{ "<itemKey>": { "hidden": bool?, "order": int? } }`, itemKey:

- `module:<moduleCode>` — модуль сайдбара;
- `section:<moduleCode>/<sectionCode>` — секция;
- `element:<moduleCode>/<sectionCode>/<elementCode>` — ссылка.

`hidden: true|false|отсутствует(наследовать)`; `order` — целое, сортировка по возрастанию,
пункты без order сохраняют базовый порядок после упорядоченных. Валидатор
(`MenuSettingsPatchValidator`) отбрасывает неизвестные ключи/поля и запрещает скрытие
пункта «Настройка меню» (см. 3.5).

### 3.3 Разрешение слоёв и применение

`MenuSettingsResolver` + `MenuSettingsApplier`, вызываются в точках сборки меню:

- `ShellComposer.buildNavLinks()` — сайдбар SDUI (`APP_SHELL`);
- компоновка SDUI-экрана модуля (OPEN `/modules/{code}`);
- легаси `GET /api/settings/modules` и `GET /api/settings/modules/{code}`.

Порядок применения для пользователя U с ролями R1…Rn:

1. **База**: хардкод модулей + сид секций/ссылок.
2. **Фильтрация по правам** (до патчей): для каждого элемента по `ModuleElementType` + коду
   проверяется эффективное право просмотра (`PermissionService` /
   `UserFullRightsResolver`; полный набор прав резолвится один раз на запрос). Нет права —
   элемент вырезается и патчами не возвращается. Секция без видимых элементов скрывается;
   модуль без оставшегося содержимого — тоже.
3. **Глобальный слой** (`default_menu_settings`).
4. **Слой ролей** — объединение по тикету: видимость считается отдельно для каждой роли
   (глобальный + патч этой роли), пункт виден, если виден хотя бы в одной роли.
   `order` при конфликте — последняя роль по алфавиту кода (как в viewsettings).
5. **Слой пользователя** (`user_menu_settings`) — поверх всего.

### 3.4 Право «Настройка меню»

- Новый `RightKind.MENU_SETTINGS` в `GLOBAL_ONLY` (`RightApplicability`) — после этого
  право можно выдать любой роли штатным механизмом (`role_permissions`), без сидов;
- у роли Администратор право есть всегда и не отключается: обладатели `hasFullRights`
  считаются обладателями права без записи в `role_permissions`;
- проверка `canManage` = `hasFullRights || hasGlobalRight(MENU_SETTINGS)`; гейт на всех
  админских эндпоинтах menu-settings (403 без права).

### 3.5 Защита от самоотстрела

Пункт «Настройка меню» (элемент в модуле Администрирование, см. 4.1) нельзя скрыть ни на
одном уровне: валидатор игнорирует такой ключ на PUT, применитель дополнительно
восстанавливает пункт для обладателей права.

### 3.6 REST-контракт

| Метод/путь                                                                              | Доступ                          | Назначение                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/menu-settings/me`                                                             | все                             | `{ "canManage": bool }`                                                                                                                                                                                                                                              |
| `GET /api/menu-settings/structure?scope=global\|profile\|user&profileKey=&userEntryId=` | личный scope — все; иначе право | полное дерево (модули→секции→ссылки: коды, nameRu/Kz, иконки) + патч слоя + эффективная видимость для превью. Право-фильтрация уже учтена: недоступные по правам пункты в структуру не входят. Для scope=user структура и превью считаются для целевого пользователя |
| `GET/PUT/DELETE /api/menu-settings/my`                                                  | все                             | личный слой текущего пользователя                                                                                                                                                                                                                                    |
| `GET/PUT/DELETE /api/menu-settings/global`                                              | право                           | глобальный слой                                                                                                                                                                                                                                                      |
| `GET/PUT/DELETE /api/menu-settings/profiles/{profileKey}`                               | право                           | слой роли                                                                                                                                                                                                                                                            |
| `GET/PUT/DELETE /api/menu-settings/users/{userEntryId}`                                 | право                           | слой пользователя                                                                                                                                                                                                                                                    |
| `GET /api/menu-settings/profiles`                                                       | право                           | список профилей (аналог view-settings `/profiles`)                                                                                                                                                                                                                   |
| `GET /api/menu-settings/users`                                                          | право                           | список пользователей (ключ + имя) для селектора «Пользователь…»                                                                                                                                                                                                      |

PUT — полная замена патча слоя; DELETE — сброс слоя. Ошибки — стандартный конверт API.

## 4. Фронтенд (fin-web)

Новая фича `src/features/menu-settings/` (SDUI-зона) + страница
`src/pages/admin/menu-settings/`. Правила: тексты через `useTranslation`/`common.json`,
кнопки `@/shared/ui/buttons`, иконки из реестра, цвета токенами, файлы ≤300 строк.

### 4.1 Точки входа (решение владельца 24.09, v2)

- **Единственный вход** — вкладка «Настройка модулей» в разделе конструктора дизайна
  (`/admin/design-constructor?tab=menu`; вкладки: «Конструктор дизайна» | «Настройка
  модулей»). Отдельной кнопки у сайдбара и отдельной страницы НЕТ.
- Пункт меню «Настройка меню» (сид бэка, модуль Администрирование → Безопасность,
  роут `/admin/menu-settings`) редиректится фронтом на вкладку.
- Обладатель права стартует с уровня «Для всех» и получает селектор уровней
  (Моё меню / Для всех / Роль / Пользователь); без права редактируется личный слой.

### 4.2 Редактор

Единый компонент-редактор (используется страницей и оверлеем «по месту»), питается от
`GET /api/menu-settings/structure`:

- выбор уровня и цели (роль — из `/profiles`, пользователь — выбор из справочника
  пользователей);
- дерево модули→секции→ссылки: клик по строке модуля раскрывает содержимое; глазик
  скрыть/показать; перестановка drag-n-drop в пределах родителя (нативный HTML5 dnd,
  без новых зависимостей — решение владельца 24.09); дубли кодов элементов из сида
  рендерятся по одному разу каждый (стабильная сортировка узлов, ключи с индексом);
- превью «как увидит пользователь» (эффективная видимость из structure);
- Сохранить (PUT слоя, полная замена) / Сбросить слой (DELETE, с подтверждением).
- Скрытые пункты показываются в редакторе приглушённо; пунктов без прав в структуре нет.

### 4.3 Применение после сохранения

По образцу `notifyViewSettingsChanged`: после PUT/DELETE — инвалидация запроса
`['app-shell']` (сайдбар перезапрашивается) и re-OPEN текущего SDUI-экрана модуля, если
открыт. Бэк отдаёт меню уже с применёнными слоями; клиентского мержа нет.

## 5. Тесты и приёмка

- **Бэк:** юнит-тесты `MenuSettingsResolver` (объединение ролей, order-конфликты, защита
  «Настройки меню», право-фильтрация, скрытие пустых секций/модулей); контроллерные тесты
  (403 без права, PUT/DELETE слоёв, structure по scope).
- **Фронт:** `npm run build` перед пушем; `npm run test:visual` при визуальных изменениях
  сайдбара (+ обновление эталонов в том же PR).
- **e2e на дев-стенде:** скрыть модуль глобально → проверить у пользователя; патч роли;
  личный слой поверх; сброс слоя; недоступность админских уровней без права; пункт
  «Настройка меню» нескрываем.

## 6. Порядок работ

1. Бэк: коды секций → таблицы/валидатор/resolver → право `MENU_SETTINGS` → REST →
   применение в четырёх точках сборки + пункт меню «Настройка меню» в сиде.
2. Фронт: API-слой и `me`-гейт → редактор → админ-страница → кнопка «по месту» →
   инвалидация после сохранения.
3. Сквозной e2e на дев-стенде, затем публикация по стандартному циклу (по команде).
